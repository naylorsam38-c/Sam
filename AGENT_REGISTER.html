Job

Orchestrator. Routes work, checks results against the goal, decides forward / back / to Sam. Every loop ends here.

Why Sonnet, fixed

Deployed rules

  • Continuity first on open

  • Never invent a detail that wasn't said; a short INTENT is correct for a vague request

Group 2 — Running, but nothing shows their output

The oversight three

These run after every session. Their prompts are the best-written in your system. review_queue appears in neither main.py nor the frontend — so all three currently work into a void.

clerk171 words · recordsRuns, unseen

Job

Writes down what happened. What was asked, in the requester's own terms. What the agent did, step by step, in order. What the result was, as stated.

Its rule

"Facts only. No assessment, no praise, no criticism, no 'successfully', no 'unfortunately', no 'correctly', no 'as expected'."

Banning the evaluative adverbs is the sharp part. "Successfully sent" is a judgment wearing a fact's clothing, and once it's in the record everything downstream inherits it.

checker371 words · extractsRuns, unseen

Job

An extraction tool. Reads text, pulls four fields — action, recipient, amount, reference — and returns JSON. Nothing else.

Its rules

  • Does not judge, advise, or explain
  • action must be a concrete verb and object — "send invoice", never "send something", never a summary
  • amount only if the text states one; digits only

Note the division: the model extracts, and compare() — plain code — decides. That's why a finding is a fact and not an opinion, and why the verdict can't drift when a model version changes.

angel384 words · judgesRuns, unseen

Job

Reads one flagged session and writes a short note for Sam. "The last set of eyes before something reaches a real customer."

Its rules

"You have NO ability to act, fix, undo, or instruct any agent. Do not write as though you can. You are writing to a person who can."

Only speaks when a check flags: intent_fabricated, mismatch, no_intent_recorded, intent_too_vague, unverified. A clean check produces no case and no noise.

The rare decision

The last three of those are "we couldn't tell" statuses, and they're treated as seriously as an outright mismatch. Almost everyone builds a checker that flags mismatches and silently passes what it couldn't evaluate — which makes "didn't check" and "checked, it's clean" look identical.

Gap

Its only write lands in review_queue, described as "only Sam's UI reads." There is no such UI. Every case it has ever raised is invisible.

Group 4 — Specified, never built

Two with full specifications waiting

observerfully specified in v3Not built

Job

A read-only auditor that watches how the system behaves over time and reports objective findings when asked. Not part of decision-making, execution or planning. "Accuracy over usefulness. No evidence, no claim."

Isolation — different shape from Builder/Tester

v3 §3 — "isolated_group: observer_readonly — one-directional. You read out of shared memory; nothing goes back in."

Never writes to any table, never edits a lesson or pattern, never joins routing or the build-test loop, never answers for another agent, never executes code, never recommends that another agent change its behaviour.

Its five thresholds

  • Duplicated effort — same problem in 3+ lessons with nothing consolidating it
  • Role drift — output diverging from its own prompt across 2+ consecutive tasks
  • Stalled pattern — 30+ days old, stale, never reconfirmed
  • Repeated friction — same Tester FAIL reason across 2+ separate tasks
  • Unactioned opportunity — recurring in 3+ lessons across 2+ agents with no task ever created

Two rules worth lifting whatever else you do

"Never lower a threshold to produce a finding. 'Nothing crossed threshold this period' is a complete answer."
"Report absence of knowledge as its own finding class — no deployment lessons, no mobile testing history, no backup validation, no disaster-recovery exercise."

The first stops an auditor justifying itself by inventing problems. The second is why its thresholds belong in SQL — the query decides whether one was met, Observer only explains what the rows mean.

Gap

slots_config.json contains zero occurrences of "observer". Every word above is sitting in a markdown file. The Clerk/Checker/Angel pipeline is a different thing — it checks one turn's intent against its outcome. Nothing watches patterns across time.

watcherbackend spec §3Not built

Job

Backend spec §3 — "For each significant piece of work, produce two independent summaries: the worker's own, and a separate watcher agent's summary of the same work. Nova cross-references the two. If they disagree, Nova flags it — this is the point of having two."

Same section, your own build note — "decide the tiebreaker when the two summaries disagree. Nova adjudicates, and if it can't resolve, it escalates to Sam rather than silently picking one. Also add red-flag alerting so anything clearly wrong surfaces immediately instead of waiting for the next minute-summary."

Why this one matters more than it looks

Your oversight compares stated intent against outcome — and both come from the same agent. That catches an agent that says one thing and does another. It cannot catch an agent that misreports what it did, because there's only one account of it.

The watcher is the second account. It's the difference between checking consistency and checking truth, and it's the single missing piece behind the whole "agents saying they did it" problem.

Gap

Never built. No prompt exists. The mind orphan above, in audit mode, is the nearest thing you have to a starting point.

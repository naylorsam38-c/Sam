The system

What it is

A personal agent system running on your own EC2 box. You talk to it in a browser on your phone. It routes what you say to whichever specialist handles it, that specialist does the work, and the result comes back on screen and out loud.

It reads your Gmail, drafts replies in your writing style, and sends them after you say yes. It remembers what it has done. It checks its own work afterwards.

The flow

What happens when you ask for something

You type on the live site | Nova receives it -- checks first for a wake or sleep phrase | Router names one worker, with confidence, and logs it | Hub locks the goal and hands off | Worker does the job, requests any action it needs | Permission layer holds the tool and the gate, re-checks your session, allows or refuses | Real service (Gmail) | Result returns through Hub | Nova shows it on screen and says it out loud | Oversight runs afterwards, in the background

Every hop writes a line to the audit log: timestamp, agent, tool, what went in, what came out.

Capability

  • Pick the right specialist for what you asked, or tell you it isn't sure
  • Read your Gmail — sender, subject, date and snippet, on request

  • Send it after you say yes — and only that exact draft
  • Remember — each worker carries its recent days; everything older is archived permanently and searchable

  • Attach apps to a room — with an honest fallback when a site refuses to embed
  • Spawn new agents from templates — unlimited, no code changes
  • Run multi-agent group threads — round-robin discussions between agents

Protection

What stops things going wrong

The login

The whole page sits behind it. Password stored as a bcrypt hash, never compared in plaintext. Five failed attempts inside fifteen minutes locks further tries. The cookie is HttpOnly, Secure, SameSite=Lax. The login session is the working session — one identity, shared with the state machine.

The permission layer

One module holds the Gmail tools and the gate. Workers can only request; the layer decides. It re-checks your session itself before it writes anything, changes any state, or touches Gmail — independently of whatever gate the route already applied.

The send gate

  • Opens only when the state is awaiting_confirmation
  • Requires an exact match from a short list — yes, yep, yeah, send it, send that, confirm, confirmed, go ahead, do it
  • Bound server-side to that one specific draft; no caller can name a different one
  • Sends an existing draft by id — never composes fresh text at send time, so what goes out is exactly what you saw
  • A near-miss re-asks rather than sending

Exactly once

Before sending, it checks for any existing in-flight or completed action against that draft. If the network reply is lost, the action stays marked in-flight and is never automatically retried — only your explicit "it didn't send" clears it. A lost reply cannot become a second email.

Timeouts

Reads, drafts and sends each have thirty seconds. The confirmation window is two minutes. A result arriving after its timeout is discarded rather than applied to a session that has moved on.

The walls

Builder and Tester see only each other. They never read the shared memory pool and nothing they say enters it. This is a branch in the code, not an instruction.

Secrets

The API key, the Google client secret and the OAuth token live in files on the box at restricted permissions. None are in the source. None are logged.

Memory

How it remembers

Working memory. Each agent carries a rolling window of its own recent daily summaries — currently four days. Summaries are written lazily, the first time a slot is used after a day went unsummarised.

The vault. When the window overflows, the oldest entries age into permanent storage. Insert-only — nothing is ever deleted or overwritten once archived.

Recall. Triggered by phrasing like "have we", "did we already", "seen this before", "any history on". The search is a plain keyword scan; the model reports only what the scan actually returned, or says No.

Style. Read once from your own sent mail, filtered for noise, bucketed by whether the recipient is work or personal. The drafting step consumes it.

Why the vault answers "No"

It cannot browse and it cannot infer. That's deliberate — a memory that returns nothing is safer than one that returns something plausible.

Oversight

How it checks itself

After every session, in the background so it never slows a reply:

  1. Clerk records what happened, facts only
  2. Checker extracts what Hub said it would do — action, recipient, amount, reference
  3. compare() — plain code, no model — decides whether the stated intention matches what actually happened
  4. ground() — also code — checks every detail against what you actually said, catching invented months, amounts and weekdays
  5. Angel writes you a note, but only when a check flags something

The verdict is code, not judgment. It passes or fails identically every time. There is a test file covering it — twenty-five cases, all passing.

The statuses it can return: checked, mismatch, intent_fabricated, intent_too_vague, no_intent_recorded, unverified. The last three mean "couldn't tell", and they're treated as seriously as an outright mismatch.

A clean session produces no case and no noise.

Interface

The front end

  • Nothing renders until the login confirms your session
  • A room per agent, each with its own transcript and its own session id
  • Nova as a still image; state shown as text — READY, SPEAKING — with no motion anywhere
  • The agent list comes from the live backend, not a hardcoded list
  • An app picker that attempts a real embed and falls back honestly when a site blocks it, with an open-in-new-tab escape
  • Replies spoken aloud through the browser
  • Local storage versioned, so a schema change wipes cleanly rather than accumulating

Improvements

Additions, in order of value

Everything above is what you have. These are additions.

  1. A screen for the oversight findings. Angel already writes them; a page that reads them makes the checking visible.
  2. Deploy the v3 prompts. Hub's response modes, the priority engine and the Builder/Tester round rules are written and ready to go on the box.
  3. Mail instructions in the mail worker's prompt. The permission layer handles the safety; the prompt can carry the job.
  4. The second summary. A watcher agent summarising the same work independently, so two accounts can be compared rather than one checked against itself. The mind prompt already on the box — "pressure-test, never flatter" — is the starting point.
  5. A liveness check. A dated question to each agent on a schedule, so a quiet agent is visibly quiet.
  6. Voice. Phone records, the box transcribes with Whisper, words go to Nova. Replaces the browser engine that iPhone Safari doesn't carry.
  7. Home-screen app. The manifest is there; the Apple meta tags and a service-worker registration complete it.
  8. A prompt editor. Edit an agent from your phone, versioned, with old versions kept.
  9. Observer. The read-only auditor, fully specified in v3, watching patterns across time rather than single turns.
  10. Auth on the remaining routes. One decorator each.
  11. Spend counter. Token counts in the audit log, so "what did today cost" is a query.
  12. A scheduler. Unlocks the per-app heartbeat and the nightly debrief.
  13. Calendar. Your own view, two-way synced.

# GOD MODE RULE — NUMBERING AND REUSE

**Status: ACTIVE.** Binding rule, not an observation. Supersedes the
"observed pattern" status recorded in `NUMBERING_REGISTER.md` §Status.

Ruled by Sam. Enforced by `assign_numbers.py` at numbering time and by
the harvester at fetch time.

---

## Rule N1 — Apps are numbered sequentially by category

Every app type gets one plain sequential number, allocated in harvest order,
carrying its category name.

```
APP-001  dating
APP-002  team chat
APP-003  invoicing
```

The number is allocated when the app's first harvest form is numbered. It is
never reassigned and never reused.

## Rule N2 — Capabilities are numbered once, globally

A capability gets **one** CAP number for its whole life, in a single shared
registry. Every app that uses that capability references the same number.

`log in` is one number. If seventy apps log in, there is still one `log in`
number, referenced seventy times.

## Rule N3 — Variants are separate capabilities, not separate copies

Where a capability genuinely differs, it is a distinct capability with its own
number — not a per-app duplicate of the same one.

The five identity types (§6: standard individual, role-based privileged,
two-sided peer, guest/anonymous, service/system) give **five** login
capabilities and five numbers. That is the complete set. An app picks the
variant it needs; it does not mint a sixth.

A new number is only ever minted when the capability does not already exist in
the registry. Everything else resolves to a number that is already there.

## Rule N4 — An app is a tree of references

An app is recorded as a tree, complete from the top down:

```
APP-003  invoicing
  screen: invoice list
    control: "New invoice"  -> CAP-0041  create record
    control: "Search"       -> CAP-0012  search records
  screen: invoice detail
    control: "Send"         -> CAP-0067  send email notification
    control: "Mark paid"    -> CAP-0044  edit record
```

Every leaf is a numbered reference. The tree is whole — app, screens, controls,
down to the individual button, and every button resolves to a capability that
actually runs.

## Rule N5 — References, never copies

No capability is ever copied into an app. Apps reuse what is in the library, in
place, where it lives. A number is an address.

Any operation that would copy a capability file into an app folder fails loudly
— naming the capability number, the source path, the destination, the
requesting app, and the reason — rather than copying.

## Rule N6 — Reserved

`CAP-0000` is globally reserved for the Shared Library Contract (§3) and is
never allocated to any app.

---

## What this replaces

The previous 100-block-per-app scheme allocated a fresh number range to every
app, which meant the same capability held a different number in every app that
used it. That is duplication by design and is now void.

The blocks recorded in `NUMBERING_REGISTER.md` (0100 todo_list … 4300
recipe_and_meal_planning) are **not reserved**. The code behind those numbers
was machine-generated by `gen_common.py`, not harvested from real permissively-
licensed Flask sources, and therefore does not satisfy
`GOD_MODE_RULE_HARVEST_ADMISSION.md`. Those numbers return to the pool.

## Enforcing checks

| Rule | Enforced by |
|---|---|
| N1 | `assign_numbers.py` — sequential allocation from the app ledger |
| N2 | `assign_numbers.py` — capability registry lookup before minting |
| N3 | `assign_numbers.py` — variant must be named, not auto-derived |
| N4 | tree build — SLOT checks, every control bound to a cap_id |
| N5 | build-side; reuse-verbatim must fail rather than copy |
| N6 | `assign_numbers.py` — `RESERVED_CAP_IDS` |

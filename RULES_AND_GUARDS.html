Command Desk

The rules, and what keeps them

The rules over every model, then each model in turn — what it does, the rules that are its own, and the guard holding each one in place.

The guards

Three kinds

Every rule in this document carries one. The tag tells you what's holding it.

GuardHow it holds
CodeA named piece of the system refuses. The model's cooperation is not required.
PromptThe instruction carries it. The model follows it because it's told to.
LogWritten down as it happens, so the pattern is visible afterwards even when no single instance trips anything.

Most of the strongest guards in this system are Code, and they cluster where they should — around anything that spends money, sends mail, or cannot be undone.

Over all of them

The rules every model obeys

RuleGuard
State only what was actually said. If a detail wasn't given, leave it out — don't guess it, infer it, or reuse it from an earlier example. Code ground() compares every stated detail against the request text. An invented month, amount or weekday is caught. Twenty-five test cases cover it.
Nothing crosses to the outside world without Sam's yes. Work freely inside the box; stop at the fence. Code The permission layer holds every outward tool. Send is uncallable unless the state is awaiting_confirmation with a matching yes bound to that draft.
Anything unclear about whether it's inside or outside is treated as outside. Prompt Stated in the build rules.
Report unknown as unknown. Never report an unchecked thing as fine. Code Oversight returns unverified, intent_too_vague and no_intent_recorded as their own statuses, each treated as seriously as an outright mismatch.
Every state change and every action is recorded. Log The audit log takes a line on every hop: timestamp, agent, tool, input, outcome.
Ask everything you need once, at the start. Don't drip questions through the job. Prompt Log Questions per task are visible in the log.
A worker never reaches a tool directly. It requests; the permission layer decides. Code The tools live in one module. No other path in the system calls Gmail.
No open channel between workers. Task down, result up, every loop ending at Hub. Code The orchestrator assembles each agent's context from an allowed set. There is no path for one worker to address another.

Model 01

nova_voicellama3.2 local → sonnet-5 on wake

The face. Takes what you say, gives the answer back out loud. Ears, mouth and screen — she doesn't decide, route, act, or hold memory. Runs free on the local model all day, and switches to the heavy model only when you say so.

Her rulesWhat keeps her to it
She never decides to wake the expensive model. Only Sam's spoken phrase does that. Code brain_mode flips on two regexes in voice_state.py, checked before the router runs. She has no path to change it.
She doesn't route, act, or hold memory — she passes things on. Code Her slot carries no tools at all. Routing happens in a separate module before she ever sees the turn.
Short and conversational. No lists, headers or markdown — it's spoken, not written. Prompt Stated plainly in her instructions.
One short clarifying question rather than guessing. Prompt
Her memory is her own line, separate from the working pool. Code Her slot is tagged to its own memory pool in the config.
Why the wake switch is guarded in code

A model able to hint its way to a more expensive tier would learn to. Putting the switch entirely outside her reach is what makes the free-all-day cost model actually hold.

Model 02

routerclaude cheap tier · its own module

Reads what you said and names which worker takes it, with a confidence. Separate from Nova and from every worker — it's a piece on its own.

Its rulesWhat keeps it to it
If it isn't clearly one worker, say so and ask. Never pick between two. Code Model-judged with no numeric threshold. There's no score to slip past at 0.51 — it returns null and the question reaches Sam.
Ordinary conversation isn't forced into a worker. Code nova_voice is one of its menu options, so plain chat resolves cleanly and confidently.
The vault is never routed to directly. Code consolidator is excluded from the menu entirely.
Every decision is written down — clean route, refusal, or parse failure. Log All three outcomes write to the audit log.
It runs on the paid tier, not the free local model. Code Pinned in config. The local model was tried and routed confidently to the wrong worker, so this is a settled decision.
A detail worth knowing

Each worker has a routing description written separately from its own prompt. Reusing the prompts caused a real misroute, because a prompt written to instruct a model reads differently from one written to tell it apart from six others.

Model 03

hubclaude-sonnet-5 · shared pool

The orchestrator. Holds the goal, hands work out, checks what comes back against that goal, and decides whether it goes forward, goes back for a fix, or comes to you. Every loop in the system ends here.

Its rulesWhat keeps it to it
Before any concrete action, state the intention: the real verb and object, plus recipient and amount if either applies. Code The line is extracted and compared against what actually happened. A missing one is no_intent_recorded; a vague one is intent_too_vague. Both raise a case.
Name the actual action — never "send something" or "do the thing". Code The extractor rejects placeholder verbs and summaries.
Use only details that were actually given. A short intention is correct when the request is vague. Code ground() catches every invented specific.
Never comment on whether its own intention was carried out. Prompt Explicit in its instructions — the checking is someone else's job, and keeping Hub out of it is what makes the check independent.
Deliver continuity first: what was in flight. Code Continuity is assembled and handed to it before the turn begins.
A specialist's output returns to Hub, not to Sam. Code Workers have no path to the user. Everything routes back through Hub structurally.
Sonnet 5, always. Never swapped down. Code Fixed in config.

Model 04

personal_assistantclaude-haiku-4.5 · shared pool

Your day — plans, schedules, reminders, follow-ups. And the mail worker: it reads the inbox, decides what matters, and drafts replies in your voice.

Its rulesWhat keeps it to it
It can request a Gmail action. It cannot perform one. Code The tool lives in the permission layer, not in the worker. It asks; the layer decides.
It never sends. Sending happens after Sam's yes and is not its decision. Code Send is uncallable unless the state is awaiting_confirmation, the captured word is on the exact list, and that yes is bound to that one draft.
A near-miss on the confirmation is never treated as a yes. Code Exact match only against nine words. "Yes but wait" and "send it later" don't match — Nova re-asks.
What gets sent is exactly what Sam was shown. Code Send takes an existing draft by id. It never composes fresh text at send time.
A lost network reply never becomes a second email. Code The action is written in-flight before the call, and an unclear reply leaves it in-flight. Only Sam's explicit "it didn't send" clears it.
Reads never touch the message body. Code Metadata only — sender, subject, date, snippet.
Drafting takes precedence over reading, so one request can't fire both. Code The draft trigger is checked first and suppresses the read trigger.
Style comes from Sam's own sent mail, not from the model's idea of him. Code The drafting step consumes a stored profile. It never infers tone itself.
A hung call can't freeze the session. Code Thirty seconds on reads, drafts and sends. A result arriving late is discarded, never applied.
Extending it is additive. Its existing behaviour is never rewritten. Prompt A standing build rule.
The most heavily guarded model you have

Nine of its ten rules are held in code. It's the only agent whose requests reach outside the box, and every one of those paths is gated by something the model can't argue with.

Model 05

builderclaude-haiku-4.5 · isolated

Design and ship in one — architecture, code, debugging, deployment. Hands finished work to Tester and reads back what Tester reports before calling anything done.

Its rulesWhat keeps it to it
It never reads or writes the shared memory pool. Code A branch in the orchestrator. When a slot is isolated, its allowed set becomes its own group — the shared pool is never assembled into its prompt.
It exchanges context with Tester only. Code Both are tagged to the same isolated group; the peer transcript is the only outside context it receives.
Nothing it says reaches Hub, Research, the assistant or the vault. Code The wall runs both ways — the contextual pool excludes anything tagged isolated.
It doesn't call its own work done until Tester reports back. Prompt

Model 06

testerclaude-haiku-4.5 · isolated

Verifies what Builder ships. Writes tests, runs them, reports bugs and regressions plainly.

Its rulesWhat keeps it to it
Never soften a failing result. Prompt Stated in its instructions, in those words.
Report pass or fail clearly, then hand findings back to Builder. Prompt
It is walled off from the shared pool, exactly as Builder is. Code Same isolation branch.
It sees Builder's work but not Builder's standing in the wider system. Code Only the peer transcript crosses.
Why these two are sealed together

Tester's job is to find Builder wrong. If both drew on the same shared memory, Tester would inherit Builder's assumptions and start checking the plan instead of the output. The wall is what keeps the disagreement real — and it's a code path, not a request.

Model 07

researchclaude-haiku-4.5 · shared pool

Digs into a topic, produces usable findings with citations when the web is available, and summarises into actions rather than walls of text.

Its rulesWhat keeps it to it
Cite sources when the web is available. Prompt
Summarise into actions, not walls of text. Prompt
Store useful findings for the vault when asked. Code Its writes route into the shared pool and age into the vault on the normal schedule.
Anything it states about the request itself must have been in the request. Code Covered by ground(), same as every other agent.

Model 08

consolidatorllama3.2 local · the vault

Holds every archived daily summary from every agent, filed by date. Answers one question: have we seen this before? It returns the material, or the single word No.

Its rulesWhat keeps it to it
It does not reason, advise, decide, merge, or offer opinions. Code The search is a deterministic keyword scan. The model is handed candidates and can only report on them — it cannot browse and cannot query.
It answers only from what it was actually given. Code Its context is the candidate set, nothing else.
It never guesses or fills a gap with something plausible. Prompt Five explicit negatives, with "No" as a permitted one-word answer.
It never acts on what it finds. Code It carries two tools, both read-only.
Sam never talks to it directly. Code Excluded from the router's menu.
It runs free, on the local model, regardless of what the rest of the system uses. Code Pinned to Ollama in config.
Nothing in the vault is ever deleted or overwritten. Code Insert-only storage.
Why "No" is the easy answer

Most memory systems make "nothing found" the awkward result, so the model reaches for something adjacent and plausible. Here the scan is dumb on purpose and "No" is one word — which is why this memory returns nothing rather than returning something wrong.

Model 09

clerkcheap tier · runs after each session

Writes down what happened. What was asked, in the requester's own terms. What the agent did, step by step. What the result was, as stated.

Its rulesWhat keeps it to it
Facts only. No assessment, no praise, no criticism. Prompt With a named list of banned words — "successfully", "unfortunately", "correctly", "as expected".
It has no opinions about what it records. Code It carries no tools and its output feeds only the comparison step.
It runs after the fact, never in the reply path. Code Scheduled as a background task so it adds no latency.
Why the banned words matter

"Successfully sent" is a judgment wearing a fact's clothing. Once it's in the record, everything downstream inherits it. Banning the evaluative adverbs keeps the record neutral enough to check against.

Model 10

checkercheap tier · extraction only

Pulls four fields out of what Hub said it would do — action, recipient, amount, reference — and returns them as data. Nothing else.

Its rulesWhat keeps it to it
It does not judge, advise, or explain. Code Its output is parsed as JSON with four keys. There's nowhere for an opinion to go.
The action must be a concrete verb and object, never a summary. Prompt With worked examples of what doesn't count.
An amount only if the text states one. Digits only. Prompt
It does not decide whether anything matched. Code The verdict belongs to compare(), which is plain code. The model extracts; the code decides.
The division that makes findings facts

A model extracts the fields; code decides whether they match. So "the amount was wrong" is a fact, not an opinion — and it can't drift when a model version changes. Twenty-five test cases lock the behaviour.

Model 11

angelcheap tier · the last set of eyes

Reads one flagged session and writes you a short note. The last read before something reaches a real customer.

Its rulesWhat keeps it to it
It has no ability to act, fix, undo, or instruct any agent — and must not write as though it does. Code No tools, no path to any agent. Its only write lands in a queue that Sam's side reads.
It only speaks when a check flagged something. Code It's only invoked on one of five statuses. A clean session produces no case and no noise.
"Couldn't tell" is treated as seriously as "was wrong". Code Three of its five trigger statuses are could-not-verify conditions.
It writes to a person, not to the system. Prompt Stated in its opening lines.
Why it can't act

The moment a checker can fix things, it starts finding fixable problems. Keeping Angel's hands empty is what keeps its findings honest.

Improvements

Guards to add, in order of value

Each of these moves an existing rule from Prompt to Code, or adds a guard where a rule currently runs on trust.

  1. A screen for Angel's findings. The checking already runs; a page that reads the queue makes it visible.
  2. A round counter on Builder and Tester. Stop at three when the same objection repeats, hard cap at five. Turns a loop rule into a wall.
  3. A repetition check. Compare a slot's last two outputs; near-identical means stuck. Catches an agent that has gone quiet in a way it can't see itself.
  4. A dated liveness question. Each agent asked something on a schedule, so a silent agent is visibly silent.
  5. Roster validation on the router. Check the returned worker name against the real list before acting on it.
  6. A banned-word scan on Clerk. The list is already written; scanning for it makes the rule airtight.
  7. An escalation table in config. Tiers read from a file rather than judged per turn, with anything unrecognised defaulting to "ask Sam".
  8. A second, independent summary. A watcher writing its own account of the same work, so two versions can be compared. The mind prompt already on the box — "pressure-test, never flatter" — is the natural starting point.
  9. Auth on the remaining routes. One decorator each.
  10. Mail instructions in the mail worker's prompt. The guards already hold; the instructions can carry the job description.
  11. A read-only connection for an auditor. Opening the database read-only makes a write refuse at the driver rather than by agreement.

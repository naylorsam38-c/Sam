## R — Records

Seven record types. Rules common to all: Sam owns all, can view/create/edit/delete all; archive
rather than delete; connected records are kept and unlinked on delete; no human-readable code needed.

### Agents

- **R.01 Represents:** a named specialist with a model, a role, and a set of things it can do.
- **R.02 Stores:** name, role, model, instructions, tools it may use, on/off, reports-to.
- **R.03 Display name:** name.
- **R.10 Stages:** running → stopped-and-reported → offline. Agents run continuously. When one stops it must report that it stopped, why, and what it could be doing instead. All agents report to Hub. Nova reports to Sam.
- **R.11 Links:** jobs, projects.
- **R.15 Extra actions:** pause. Must exist as a button AND be voice-commandable through Nova.

### Conversations

- **R.01 Represents:** a single thread between Sam and one agent, kept so it can be picked up later. Hub must know what has been discussed across all of them and keep reminding Sam what he has missed.
- **R.02 Stores:** which agent, when, the messages, what came of it, whether Sam has read it. Written automatically by the system — never typed by Sam.
- **R.03 Display name:** topic.
- **R.10 Stages:** open → needs attention → closed.
- **R.11 Links:** jobs.

### Jobs

- **R.01 Represents:** one piece of work an agent is doing.
- **R.02 Stores:** which agent, what was asked, status, result, timestamps.
- **R.10 Stages:** queued → running → done / failed.
- **R.11 Links:** agents, projects, conversations, documents.
- **R.15 Extra actions:** retry. Button and voice.

### Projects

- **R.01 Represents:** a group of jobs and conversations under one goal. Selecting a project sets context system-wide.
- **R.02 Stores:** name, goal, status, what is linked.
- **R.10 Stages:** active → paused → finished.

### Memory entries

- **R.01 Represents:** what Hub stores and recalls.
- **R.02 Stores:** content, when, which project, which agent.
- **R.10 Stages:** none. Additive only. Never deleted. Written by the system, read on lookup.

### Linked services

- **R.01 Represents:** a connected account (Gmail, calendar) OR a pasted API key (Tavily search, model providers).
- **R.02 Stores:** which service, its token or key, which agent uses it, whether it is live.
- **R.10 Stages:** connected → expired → disconnected.

### Documents

- **R.01 Represents:** a file Hands works on.
- **R.02 Stores:** the file, its type, status, which job.
- **R.10 Stages:** received → filled → signed → done.
- **R.15 Extra actions:** open source document. Button and voice.

## Requirements that came out of the interview but have no question

These are real requirements Sam stated. The interview had nowhere to put them.

1. Agents run continuously and self-report when they stop, with a reason and a suggestion of what they could be doing.
2. Hub tracks every conversation and reminds Sam what he has missed.
3. Every extra action is both a button and a voice command through Nova.
4. Browser badge inside real Gmail: tap it on a thread, tell the agent "draft this", the draft lands in Gmail itself, not in the app. On phone this is the native app with an in-app browser.
5. "Lives online" must trigger a connect-a-host flow (connect button → sign up with host → authorise → token returns → deploy runs), not just record a word.

## Flaws in the interview Sam identified

1. Many questions are builder's questions dressed as user questions. A person cannot answer them differently, so they should be defaults shown once at the end — not asked. Named: stage transitions (rewrite as "what needs your approval before it happens?"), C.02, C.03, A.14.
2. The visual side answers what text cannot. Talk for the structure, look for the rest.
3. Ask as if the asker has no background knowledge of the product.
4. The 122 were derived from five database-shaped apps. They cover CRUD well and agent-shaped apps badly — nothing asks what an agent does, how Hub decides, or what happens when work fails halfway.
5. Fix: build Command Desk, then lock it as the sixth template — the agent-app template — so the next agent-shaped build starts from a proven structure.

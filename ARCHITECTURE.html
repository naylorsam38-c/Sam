Plus one that isn't in the slot list and matters more than most of them:

The router

Pinned to Claude's cheap tier, not to Ollama — and that was the right call. llama3.2 was tried first and confidently misrouted a plain "what's come in" to Builder, with a fabricated justification attached.

That's the failure mode worth understanding: it didn't fail loudly, it failed persuasively. A small local model will follow instructions right up until the moment it doesn't, and then explain itself fluently. Routing is a control-plane decision — every downstream cost is determined by it — so paying fractions of a cent for reliable instruction-following there is one of the best trades in the system.

The other good decision in the router: it's model-judged, not threshold-based. It returns "worker": null when genuinely torn between two workers, rather than picking whichever score was highest. A numeric threshold gives you a confident wrong answer at 0.51. A model told to say "I don't know" gives you a question. And nova_voice is one of the menu options, so ordinary conversation resolves cleanly rather than being forced into a worker.

Small thing, real consequence

Each slot has a routing description separate from its own prompt.txt. That exists because reusing the prompts verbatim caused a real misroute — "what's come in" matched Hub, because Hub's own opening line reads as a semantic match too. A prompt written to instruct a model is not a prompt written to distinguish it from six others. Two different jobs, two different texts.

Part 02

The walls, and why they exist

Your isolation model is more sophisticated than most systems I see, and it's the part worth understanding properly, because it's the part that stops the failure you already had.

Three memory pools, not one

PoolWho's in itSees
hubhub, research, personal_assistant, consolidatorThe shared contextual pool — continuity, relevant memory, related decisions
isolatedbuilder, tester (build_test)Only each other's transcript. Never the shared pool.
nova_voicenovaIts own line, kept separate from the working pool

In orchestrator.handle_turn this is a genuine branch, not a prompt instruction: if the slot is isolated, allowed becomes its group members and it reads peer_transcript. If it isn't, allowed becomes the contextual slots. An isolated agent cannot see the shared pool because the code never puts it in the prompt — not because it was asked not to look.

A wall made of code is a wall. A wall made of instructions is a request.

Why builder and tester are sealed together

Builder and Tester are adversaries by design. Tester's job is to find Builder wrong. If both draw from the same shared memory, three things go wrong, and they go wrong quietly:

  • Contamination. Tester reads Builder's reasoning and inherits its blind spots. It stops testing the code and starts testing the plan — agreeing with the assumptions instead of checking the output.
  • Collusion. Two agents optimising for "resolve this loop" converge on agreeing. Not maliciously — agreement is the cheapest path to a finished-looking state.
  • Pollution. Their round-by-round argument floods the shared pool that Hub and the assistant depend on, and the signal-to-noise of everything else drops.

Sealing them in a two-member group means their loop is loud inside the box and silent outside it. That's exactly right.

The straight line, and the incident that proves it

Sam | Nova (I/O only -- decides nothing, holds nothing) | Router (names a worker + confidence, logged every time) | Hub (goal locked here; checks results against the goal) | Worker (does the whole job, requests actions) | Permission layer (holds the tool AND the gate) | Real service

Task goes down. Result comes up. Every loop ends at Hub, and Hub answers to you. There is no sideways link — no open channel where workers talk to each other unsupervised.

30 July — why this rule is in your documents

Builder and Tester froze on a stale refusal. An external "scheme to make money without Sam" message lodged in their rolling context and re-fired at every call for days. They correctly refused it — and then couldn't move past it, because nothing cleared the context and nothing noticed they'd stopped producing.

Three separate lessons, and your architecture now answers all three: an open agent-to-agent channel is an attack surface; rolling context needs an eviction path, or one bad turn is permanent; and a stuck agent looked identical to a working one, because nothing was checking liveness. The login gate stops the first. The rolling window bounds the second. The third is still open — see Part 07.

Memory: two tiers, and a deliberately stupid vault

Each worker carries a rolling window of its own daily summaries — nothing else, by default. When that window overflows, the oldest entries age into the vault, which is insert-only; nothing is ever deleted or overwritten once archived.

The part I'd single out: the vault agent doesn't reason. vault_search is a plain deterministic keyword scan. The model's only job is to confirm what the scan actually found, or say a clean "No." It cannot free-browse and it cannot infer.

That's a genuinely good instinct, and it's the opposite of how most people build memory. Semantic retrieval that "helpfully" surfaces adjacent-but-wrong context is one of the most common sources of confident nonsense in agent systems — the model can't tell that what it was handed isn't what it asked for. A dumb scan returns nothing rather than something plausible, and nothing is a much safer failure.

Part 04

The hard problem: it says it did it

This is the thing you asked about, and it's the central unsolved problem in agent systems. Not hallucinated facts — hallucinated work.

Why it happens

A model completing "I've updated the config and verified the tests pass" is doing exactly what it does with every other token: producing the most plausible continuation. Nothing in that process consults the filesystem. There's no internal flag separating "I did this" from "this is what doing it would look like." The report and the work are generated by the same machinery, so a confident report is not evidence of work — it's evidence that a confident report was the likely next thing to say.

It gets worse under exactly the conditions you care about: long tasks, where the model is far from the original instruction; failure, where reporting success ends the interaction and reporting failure invites more work; and vague goals, where "done" is undefined so anything can satisfy it.

Never ask a model whether it did the work. Ask the system what changed.

Three levels of verification

LevelWhat it isWorth
Self-report"I've done it, tests pass"Zero. Not weak evidence — no evidence.
Model judgeA second model reviews the first's outputReal but limited. Catches obvious drift; shares blind spots; biased toward long, confident answers.
Ground truthExit codes, database rows, file hashes, HTTP status, a diffThe only thing that actually settles it.

The discipline that separates working systems from demos is simple to state and unpopular to implement: define "done" as a machine-checkable predicate before the work starts. Not "improve the login flow" — "an unauthenticated POST to this route returns 401, proven by this command."

Your COMMAND doc already says this — "Done" means proof, not "the code ran" — and your roadmap's Done when lines are exactly the right shape. That instinct is ahead of most teams.

Where your oversight lands

Your Clerk / Checker / Angel pipeline is a genuinely good instance of level two, with one crucial detail most people get wrong: the verdict is not in the model. compare() and ground() are deterministic functions. They pass or fail identically forever, and there's a test file proving it — I ran it, 25 of 25.

The design decision underneath that is the important one. The model extracts fields; code decides whether the fields match. So "the amount was wrong" is a fact, not an opinion, and it can't drift when a model version changes.

The three statuses I'd single out

unverified, intent_too_vague and no_intent_recorded are treated as seriously as an outright mismatch. That's the rare move.

Almost everyone builds a checker that flags mismatches and silently passes anything it couldn't evaluate — which means the cases where the system couldn't tell whether something went wrong look identical to the cases where nothing did. Your system refuses that. "I don't know" is a finding.

Where the gap still is

Your oversight compares stated intent against outcome. That catches an agent that says one thing and does another. It does not catch an agent that misreports what it did — because both the intent and the report come from the same agent. If it lies consistently, the comparison passes.

That's precisely the second check your backend spec asked for and nobody built: a separate watcher summarising the same work independently. Two accounts from two sources, cross-referenced. It's the difference between checking consistency and checking truth.

The arithmetic nobody likes

Per-step reliability compounds. A model that's right 95% of the time, over a twenty-step task, finishes correctly about 36% of the time. At 99% per step you're still only at 82%.

You don't fix that with a better prompt. You fix it structurally:

  • Fewer steps. Every step you can move from the model into code is a step that can't fail probabilistically.
  • Checkpoints. Verify at boundaries so an error can't propagate twenty steps before anyone notices.
  • Idempotence. Make retry safe, so recovery doesn't cause a second failure. Your exactly-once send guard is this pattern.
  • Fail closed. When uncertain, stop. Your in_flight handling — never auto-retry, wait for a human — is the correct shape.

Part 05

What the field actually does

Honest version, including where the consensus is contested and where I'm giving you my read rather than an established fact.

The main argument: one agent or many

There's a real split among people shipping this stuff. Anthropic published on a multi-agent research system where an orchestrator spawns parallel subagents and reported large gains over single-agent on breadth-first research. Cognition published a well-argued piece — Don't Build Multi-Agents — arguing the opposite: that splitting work across agents fragments context, and that a single agent with well-engineered context beats a committee.

Both are right about different shapes of problem, and the distinction is sharper than the debate usually makes it:

Multi-agent winsSingle agent wins
Read-only, parallel, breadth-firstAnything with shared evolving state
Subtasks genuinely independentLater decisions depend on earlier ones
Results merge cleanlyMerging requires judgment
Search, research, wide sweepsWriting, editing, building

Your system is the right shape. It isn't a committee — it's orchestrator-and-workers with one decision-maker. Nova doesn't decide, the router names one worker, one worker does the whole job, the result returns through Hub. Nobody merges conflicting opinions. The one place you deliberately run two agents against each other is Builder/Tester, where disagreement is the product.

What the failure looks like when people get this wrong: five agents each holding a slightly different idea of the goal, producing five plausible outputs that can't be reconciled — which is a fair description of the thing you said you didn't want. Ten designs for the front entry.

Context engineering has replaced prompt engineering

The consensus shift over the last while is that the binding constraint isn't instruction wording, it's what's in the window. Long contexts degrade — attention spreads, middle content gets lost, contradictory old turns compete with current ones. More context is not better context.

What people do about it: bounded rolling windows with real eviction; summarising a completed phase into a compact note rather than carrying the transcript; keeping durable state in a database and reading only what this turn needs; and giving each agent the narrowest view that lets it do its job.

Your reads_context / writes_context declarations per slot are this pattern, done declaratively. That's ahead of the curve — most systems shove one growing blob at every agent.

Determinism at the edges, model in the middle

The most consistent finding across teams that got things working: use code for control flow and models for judgment. Loops, retries, branching, ordering, permissions, validation — all code. The model decides what a message means, or which of these is the right approach, and hands the decision back as a typed value.

Your COMMAND doc's prime directive is a sharper statement of this than most engineering blogs manage: if a rule ends up only in a system prompt when it could have been code, config, or a DB grant, the step is not done.

Tools: fewer, sharper, with error messages that teach

  • Fewer tools beats more. Selection accuracy falls off as the menu grows. Ten well-named tools outperform forty overlapping ones.
  • Validate at the boundary. Schema-enforced arguments, rejected before execution. Never trust the shape of what a model hands you.
  • Errors should be instructive. "Missing required field 'recipient'" gets a correct retry. "Error 400" gets three wrong ones.
  • Name for the model's mental model, not the database's. send_existing_draft is unambiguous; execute_action invites misuse.

Human-in-the-loop, on a clean line

Universal across every serious deployment: irreversible actions stop for a human. The good implementations draw the line the way yours does — by whether the effect leaves the system, not by whether the action feels significant. Work freely inside; stop at the fence. Anything unclassifiable is treated as outside.

The pattern people converge on: propose, show the exact artifact, capture explicit consent bound to that artifact, execute once, record. You built that. Most teams discover it after an incident.

Evals: the thing everyone skips

The single biggest difference between systems that stay working and systems that rot is a test set of real cases with known-correct outcomes, run on every change. Without it you're tuning prompts by vibe and discovering regressions in production.

Nobody enjoys building this and almost everyone regrets not having it. Twenty real cases beats a thousand synthetic ones. Your test_compare.py is the seed of exactly this — the same idea applied to routing decisions and to worker outputs is the highest-leverage thing missing.

Observability: traces, not logs

You need to answer "why did it do that" for a specific past turn. That means a full trace — input, retrieved context, model, tool calls, results, output — reconstructable and replayable. Logs tell you what happened; traces tell you why.

Your audit log is most of the substrate. What's missing is a way to look at it, which is the same gap as the review queue having no screen.

Where I'd flag uncertainty

This field moves fast and a lot of published practice is one team's experience generalised. The parts I'd call solid: determinism over model self-report, human gates on irreversible actions, evals, context discipline, and the reliability arithmetic. The parts still genuinely contested: how many agents, how much memory autonomy, and whether long-horizon self-correction works without a human in the loop. Treat confident claims in either direction — including some of mine — as provisional.

Part 06

Brain to face

Where most of these systems actually fall over — not the reasoning, the seam between the reasoning and the person.

The interface must never claim what the backend hasn't confirmed

The commonest UI sin in agent products: showing "Sent ✓" when the request was issued rather than when it completed. Optimistic UI is fine for a like button. It is not fine for something that leaves the building.

Your backend already models this correctly — in_flight exists precisely because "we asked" and "it happened" are different states. The interface has to carry that honesty through: sending, sent, and unconfirmed — check before retrying are three different messages, and the third one is the one that saves you.

Show the work

Systems people trust surface what the agent is doing as it does it — which worker took it, which tool was called, what came back. Not for debugging. Because a visible chain of steps is checkable, and a paragraph of prose is not.

This is also the cheapest defence against the Part 04 problem. An agent that reports "I checked your inbox" alongside a visible gmail_read → 3 messages line is making a claim you can audit at a glance. Hide the machinery and you're back to taking its word.

Latency is a design constraint, not an engineering detail

Perceived speed is dominated by time-to-first-token, not total time. Streaming a reply that takes eight seconds feels better than a spinner that takes four. For voice the budget is brutal — much beyond a second of silence after you stop speaking reads as broken, which is why real-time voice stacks stream every stage and start rendering before the sentence is finished.

The corollary for your build: the moment Nova gets a real microphone, every stage needs to overlap. Transcribe while they're still talking, start generating on the first finalised sentence, speak the first sentence while generating the second.

Voice-specific things that bite

  • Barge-in. If you can't interrupt it mid-sentence, it feels like a recording. Cancel generation and playback the moment speech is detected.
  • Turn-taking. Deciding you've finished speaking is genuinely hard. Silence detection alone cuts people off mid-thought.
  • Transcription garbling consent. Your documents already caught this — a near-miss on the yes-list must re-ask, never infer. That's one of the sharpest lines in your spec.
  • Voice hides state. Screens show status for free; speech doesn't. Which is a good argument for your panel and Nova working together rather than voice alone.

On the ten designs for the front entry

What you described is a real and well-known failure, and it isn't fixed by better prompts. It's fixed by the same two moves as everything else here: one decision-maker, and a machine-checkable definition of done before work starts.

Your architecture already has the first. The seven front-end builds in circulation are what the second one's absence looks like — each one plausible, each one finished by somebody's standard, none of them the answer, because "the home screen" was never defined as something you could pass or fail.

Part 07

What I'd change, ranked

From this analysis specifically — not a repeat of the roadmap's ordering.

  1. Give the oversight findings a screen. You built a verification system whose output nothing can display. Every hour it runs is currently wasted. This is the highest-value hour on the list.
  2. Add liveness checking. The 30 July freeze went undetected because a stuck agent and a working one look identical from outside. A dated health question to each slot, and an alert when one stops answering, closes the third lesson from that incident — the only one still open.
  3. Move escalation from prompt to code. The last row of the guardrail table. It's the difference between a rule and a description.
  4. Build the second summary. Intent-versus-outcome catches drift; it can't catch consistent misreporting. Two independent accounts is the check you specified and don't have.
  5. Start an eval set. Twenty real routing decisions with the correct worker recorded. Run on every prompt change. You already have the pattern in test_compare.py — this applies it where the decisions actually get made.
  6. Surface the chain in the UI. Which worker, which tool, what came back. Trust and debuggability from the same change.
  7. Add an eviction path to rolling context. The 30 July message stuck because nothing could remove it. A way to clear a slot's context without restarting is a five-minute fix for a problem that cost you days.
What not to change

The permission layer's independent re-validation. The exactly-once send guard. The refusal to auto-retry an unconfirmed send. The deterministic vault scan. The Builder/Tester wall. The router on a paid tier. The deterministic oversight verdict.

Every one of those is a decision a lot of teams get wrong, and several of them look like over-engineering right up until the day they don't. Whoever built this understood the difference between a system that works and a system that appears to work — which is the whole subject of this document.

The safety work is genuinely good. The permission layer re-validates the session independently before any Gmail call, the send gate binds a confirmation to one specific draft, a lost network reply is never retried, and the part of oversight that decides whether something went wrong is deterministic and tested. That core is worth keeping.

What's weak is everything you actually touch. Oversight produces findings no screen can display. The mic doesn't work and can't, as built. The home-screen app won't install. There's no way to edit an agent's prompt without going to the box. The system is more finished underneath than it is in front of you.

Throughout

The rules that apply to every phase

Taken from your own build documents. These don't change between phases.

  1. The live system is the only truth. Never deploy from a zip, a backup, or memory. If the box contradicts a document, the box wins — stop and report.
  2. Back up before touching anything, and confirm the backup restores. A backup you can't restore isn't a backup.
  3. New capability goes in new files. Never overwrite the existing hub or agents. Extend by adding a path, not by rewriting.
  4. One stage at a time. Finish it, prove it, stop, wait. Never build two unknowns at once.
  5. "Done" means proof, not "the code ran." HTTP 200 means the page loaded, not that it works. Nobody can see your phone — you are the final eyes.
  6. Reverse-engineer the task before starting it. What's unclear, what would have to be guessed, what costs money, what can't be undone, what needs you specifically. Ask it all once, up front.
  7. Anything leaving the box needs your yes. Working inside the box is free. Crossing the fence stops.
  8. The audit log is always on. Every state change and action: timestamp, state, trigger, result.
  9. Rules that can be enforced must not live in prompts. If a rule could be code, config or a database grant and it's only in a prompt, the step isn't done.

3.1The live prompt editor — never builtMissing

Two separate roadmaps require it and it does not exist. I enumerated every route in main.py: there is no GET or PUT for an agent's prompt anywhere. Today, changing how an agent behaves means going to the box.

Build it as specified: per-agent get and put, gated to you only, versioned — bump on every save, all prior versions immutable and retrievable, and reject a save that would overwrite without a bump.

Treat this as a privileged write. An endpoint that rewrites an agent's instructions is the single most valuable thing for an attacker to reach.

Done whenyou edit Hub's prompt from your phone, the next call reflects it, and a task created before the edit still reports the old version with the old text retrievable.

Phase 4

The enforcement core — on SQLite

3 days

The valuable half of the big roadmap, and none of it needs Postgres. Your permission layer already does exactly this for Gmail. This generalises it to everything else.

4.1policy.yaml and a loader that fails closedNot started

One file holding escalation tiers, priorities, loop rules and thresholds. The loader validates at startup and refuses to start on a malformed file rather than falling back to defaults.

The line that matters: an unknown action returns require_approval. An action nobody anticipated must never default to permitted.

Done whenget_escalation_tier("an_action_that_does_not_exist") returns require_approval, proven by a test.
4.2One execution path for every side effectNot started

Every agent action routes through enforcement.py, which checks policy before the action runs. Silent tiers execute and log. Notify tiers execute, log and emit. Approval tiers do not execute at all — they persist a pending record and hand control back to you.

Fail closed on error: if the policy lookup itself throws, the action does not run. This middleware becomes a single point of failure, so its failure mode has to be "nothing happens," never "everything is allowed."

Then audit for bypasses. Every file write, HTTP call, database mutation and outbound message reachable without passing through this path is a hole. List any that can't be routed yet rather than quietly leaving them.

Done whena test agent told to delete a file cannot — even with its prompt edited to say approval isn't needed. Prompt says yes, enforcement says no, no happens.
4.3Version stamps on every writeNot started

Four strings — prompt, policy, schema, runtime — stamped by one write helper on insert. Existing rows backfill to 0.0.0, honestly marking them as pre-versioning rather than pretending.

This is what turns your audit log from a list into a record. Without it you can't tell which prompt or which policy produced a given decision — and it's what makes the prompt editor in 3.1 auditable rather than just convenient.

Done whena new row carries four real version strings without the caller passing them.
4.4Observer isolation, the SQLite wayNot started

The big roadmap wants a Postgres role with SELECT-only grants and calls it the one guarantee that survives prompt injection. You can't have that on SQLite — no users, no GRANT.

What you can have: open Observer's connection as file:aire.db?mode=ro. A real refusal from the driver, not the application promising to behave. Weaker than Postgres — same file, no per-table control — but far stronger than a rule in a prompt.

Done whenan INSERT on Observer's connection raises from sqlite3 itself, proven by a test.
Why this sits here

Every backend feature added after Phase 4 inherits the enforcement path automatically. Anything added before it has to be retrofitted. Phases 2 and 3 are safe to do first because they're the front end and the model config — they don't add new side effects.

A systemd timer or APScheduler inside the core process. Every job routes through enforcement.py from Phase 4 — a background job that can act unsupervised is exactly what shouldn't get its own private path.

Done whena trivial job fires on schedule and its run appears in the audit log.
5.2Per-app status updatesNot started

A running account of what each worker has done in each app — "checked 3 emails, drafted 1 reply, nothing sent" — roughly once a minute. Not a live view, a steady heartbeat. Nova reads these and knows the state of play without operating anything. Everything needed is already in the audit log; this is a rollup on a timer feeding the panel from 2.6.

Done whenthe panel shows a running per-app account that updates without you asking.
5.3The nightly debriefNot started

Nova and the memory agent run a nightly pass: anything untouched lately, anything missed, anything old worth following up. The memory agent retrieves; Nova decides. Memory surfaces, the hub judges — that separation is the point.

Done whena debrief runs unattended overnight and its output is waiting in the morning.

Phase 6

Oversight, as originally specified

4–7 days

What got built is good but it isn't what the backend spec described. The spec wanted two independent accounts of the same work, cross-referenced. What exists compares stated intent against outcome — valuable, but a different check.

6.1The hub's own read-only view of each appNot started

From the spec: a link separate from the worker's, so you can ask Nova "what's been done in Gmail today?" and get a straight answer. The hub observes, the worker acts, and the wires don't cross.

This pulls against the current design, which deliberately funnels all Gmail through one path. The honest version is a read-only view over the audit log and actions table — same answer, no second credential to secure.

Done whenasking Nova what happened in an app today returns a real account drawn from the log.
6.2Two independent summariesNot started

The worker summarises its own work. A separate watcher agent summarises the same work. Both roll up. This catches a worker that misreports, not just one that drifts from its stated plan — genuinely different from what's built.

Done whenone piece of work produces two summaries from two different agents.
6.3Nova adjudicates, and escalates when she can'tNot started

If the two agree, fine. If they disagree, Nova flags it — that's the whole point of having two. Your own build note asks for the tiebreaker to be explicit: Nova adjudicates, and where she can't resolve it she escalates to you rather than silently picking one. Today Angel writes to a queue with no adjudication step and no path back through Nova.

Done whena deliberately mismatched pair produces a flag, and an unresolvable one reaches you.
6.4Red-flag alerting — blocked on 0.5Your call

The spec wants anything clearly wrong to interrupt immediately, because a one-minute cadence can miss a fast mistake. The v3 prompts say nothing is ever pushed.

A reasonable resolution: both are right about different things — routine findings stay pull-only, and one narrow class (an action that already crossed the fence and shouldn't have) interrupts. But that's your call, not the builder's.

Done whenthe rule is written down once, and the code matches it.
Phase 7

Calendar

1–2 weeks

The one item in the backend spec never started at all. It's also the hardest thing on this list, and it's worth being blunt about why.

Email works as text — the message that arrived, the reply that was drafted, side by side. Calendar doesn't. You need to see it, and Google Calendar won't embed. So it has to be Command Desk's own view backed by a genuine two-way sync.

Two-way sync is where projects like this die. Not the reading, not the writing — the reconciliation. An event changed in both places between syncs. A deletion that might be a deletion or might be a failed fetch. Recurring events, where one edit can mean this instance, all instances, or this and everything after. Time zones across daylight saving. None of it is exotic; all of it has to be decided rather than discovered.

7.1Read-only calendar view firstNot started

Pull events, render a real view, let agents read it to brief and plan. No writes. Same shape as Stage 3's read-only Gmail proof, and for the same reason: prove the connection where nothing can be damaged.

Done whenyour real week renders in Command Desk and Nova can describe your day.
7.2Writes, behind the gateNot started

Creating or moving an event has consequences — it lands in someone else's calendar. Through the permission layer, behind confirmation, exactly like send. Same exactly-once guard: a lost network reply must never become two meetings.

Done whenyou speak an event, see it, confirm it, and it appears in Google Calendar once.
7.3Two-way sync and conflict resolutionDesign first

Decide the rules before writing code: which side wins a simultaneous edit, how a deletion is told apart from a failed fetch, what happens to recurring-event edits, how far back a sync reaches. Write them down, then build to them.

Done whena change in either place appears in the other, and a deliberate simultaneous edit resolves the way the written rule says.
Phase 8

The Postgres question

3–6 weeks — conditional

The final roadmap assumes PostgreSQL throughout: roles and grants, jsonb, timestamptz, row-level security, Terraform, RDS. You're on SQLite. This is where that gets resolved — or deliberately doesn't.

Ask this before committing

Row-level security, tenant_id and Postgres roles exist to keep different customers apart. If Command Desk is one person on one box, that's a month spent on a problem you don't have yet — and one you can solve later, when a second user is real rather than hypothetical.

Phase 4 already gives you the fail-closed policy engine, the single enforcement path and a real read-only handle for Observer. That's most of the protection, for about three days.

If you do go ahead, the order is fixed and the migration itself is the risk — moving a live database with real sessions, real memory and a real inbox history is a project in its own right, not a step.

  1. Reversible migrations first. Every migration gets a matching down script, applied as an atomic batch, tested up-then-down against a clean database in CI before anything touches AWS. One untested down script is the difference between a bad afternoon and a disaster.
  2. Event bus. Eleven event types, persisted with version stamps, indexed on the unhandled-queue lookup because it runs constantly. Hub subscribes rather than polls.
  3. Hub's completion guarantee. A background processor works unhandled events oldest-first to a resolution — completed, escalated, or explicitly superseded. Never blocks foreground work. A pending approval past its 72-hour expiry escalates; never auto-approved, never quietly dropped.
  4. Observer as a real database role. SELECT only, on named tables, public grants explicitly revoked, credentials in Secrets Manager, created by a migration so it's reproducible. The step Phase 4 could only approximate.
  5. Thresholds as SQL. Five parameterised queries with values injected from policy. The query decides whether a threshold was met; Observer only explains what the rows mean.
  6. Decisions table. Evidence references required — a decision with no evidence isn't recorded as a decision. Three confidence values stored separately, never averaged into one.
  7. Health as counts. If a number can't come from a live query it isn't displayed. No percentage without both numerator and denominator visible. An empty result shows "no data" — never 0%, never 100%.
  8. Semantic judgments as fields. The model writes drift_detected, same_issue_as_prior, role_drift. Policy decides the consequence. The prompt holds the judgment and never the consequence.
  9. Slim the prompts — last. For every remaining sentence, ask whether it's enforced somewhere. If it is, delete it from the prompt. A rule stated twice drifts out of sync.

Open

Decisions nobody else can make

  • Which interface is the target — Nova alone with a mic and one panel, or rooms with tiles and an app launcher. Two documents describe two products.
  • Memory window — fourteen days as the backend spec says, or four as the code says.
  • Alerting — interrupt on a red flag, or on demand only. Phase 6.4 waits on this.
  • The two Llama slots — which variant, self-hosted or hosted.
  • Builder / Tester split — implement the cheap-sharp difference, or delete the claim.
  • Postgres — migrate, or stay on SQLite and accept the weaker Observer boundary.
  • Second worker — which service Stage 5 clones to.
  • Retention — how long conversations, planners and threads are kept. Design it as a setting, not a hardcode, and tune by trial.
  • Vault placement — separate agent or folded into the hub. Your stated lean is separate, to keep load off Nova.
  • Calendar conflict rules — which side wins, and what a deletion means. Decide before 7.3, not during.

Out

Ruled out — do not build

  • Claude or ChatGPT running inside Command Desk as embedded apps, and any attempt to wire Claude-with-its-full-tools into the system. You wanted a closed loop with Claude keeping its native tools; it isn't available, and you've decided. They can still appear as pickable apps — the "operates them live in the frame" path is not a target.
  • Anything relying on embedding an app that blocks it. Assume Gmail, Calendar and Maps cannot be shown in an iframe. The backend link plus per-app updates is the substitute.
  • Video Nova. Dropped entirely. The original still image, no loop, no motion.
  • Browser-based speech-to-text. The engine doesn't exist in iPhone Safari. Phase 2.2 replaces it with recording on the phone and transcribing on the box — that's the fix, not a rebuild of the same dead thing.
  • Rebuilding the permission layer, state machine, auth or oversight. They work, they're tested, and replacing them would cost weeks to land somewhere worse.
  • Downgrading the router to Ollama. Tried; llama3.2 misrouted with a fabricated justification. The small per-call cost buys instruction-following reliable enough that "never guess" is actually true.

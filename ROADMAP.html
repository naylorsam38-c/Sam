The safety work is genuinely good. The permission layer re-validates the session independently before any Gmail call, the send gate binds a confirmation to one specific draft, a lost network reply is never retried, and the part of oversight that decides whether something went wrong is deterministic and tested. That core is worth keeping.

What limits you is underneath it: a single box, a SQLite file, two processes where one would do, and nothing anywhere that can wake up on its own.

Throughout

The rules that apply to every phase

Taken from your own build documents. These don't change between phases.

  1. The live system is the only truth. Never deploy from a zip, a backup, or memory. If the box contradicts a document, the box wins — stop and report.
  2. Back up before touching anything, and confirm the backup restores. A backup you can't restore isn't a backup.
  3. New capability goes in new files. Never overwrite the existing hub or agents. Extend by adding a path, not by rewriting.
  4. One stage at a time. Finish it, prove it, stop, wait. Never build two unknowns at once.
  5. "Done" means proof, not "the code ran." HTTP 200 means the page loaded, not that it works. Nobody can see your phone — you are the final eyes.
  6. Reverse-engineer the task before starting it. What's unclear, what would have to be guessed, what costs money, what can't be undone, what needs you specifically. Ask it all once, up front.
  7. Anything leaving the box needs your yes. Working inside the box is free. Crossing the fence stops.
  8. The audit log is always on. Every state change and action: timestamp, state, trigger, result.
  9. Rules that can be enforced must not live in prompts. If a rule could be code, config or a database grant and it's only in a prompt, the step isn't done.

Phase 0

Phase 0

Close what's open

1 day

Nothing new gets built until these are shut. Every one of them is small, and two of them are live exposures.

0.1Shut the unauthenticated chat pathBroken

/commanddesk/chat reaches the brain with no login. nginx sends it to the adapter, the adapter proxies to core's /api/chat, and nothing on that path checks a session. Anyone who finds the URL spends your API budget and can write into session continuity.

Two ways to fix it. Add Depends(require_auth) to the core route — or delete the adapter's /chat proxy entirely, since your live front end talks to /nova/turn and doesn't use it. The second is better: it closes the hole and removes dead weight.

Done whencurl to /commanddesk/chat with no cookie returns 401, and the live front end still works unchanged.
0.2Rotate the login passwordBroken

The seed credential sits in core/auth.py as a cleartext constant and is written into the build document. Both have travelled in zips. seed_default_user only inserts when the row is missing, so changing the constant alone changes nothing — the stored hash has to be replaced.

Done whenthe old password fails on the live login, the new one works, and the constant no longer matches anything real.
0.3Restore the single-Gmail-path ruleBroken

The snapshot says one code path touches the Gmail API. There are two — style_profile.py builds its own service and reads your sent mail. It's auth-gated at the route and it writes to the audit log, so it isn't a hole, but it skips the permission layer and so leaves no action record and gets no independent session check.

Either route it through the permission layer as a third tool, or write down explicitly that it's a second sanctioned path. What can't stand is a documented invariant that isn't true.

Done whenevery Gmail call either passes through permission_layer, or is named in the docs as a deliberate exception.
0.4Gate the legacy routesHousekeeping

/api/tools, /api/groups, /api/agents/*, /api/memory/*, /api/decision and /api/nudge have no auth. They're reachable only from the box — core binds loopback and nginx proxies just three prefixes — so this isn't urgent. It is one decorator each, and it removes the question permanently.

Done whenevery route either requires auth or is listed as deliberately public with a reason.
0.5Settle two contradictions in your own documentsYour call

Memory window. The backend spec says fourteen daily summaries. The code says four, and the snapshot calls four the locked figure. It's an environment variable, so it's a one-line change — but decide which is real.

Alerting. The backend spec wants red flags that interrupt immediately. The v3 prompts say nothing is ever pushed, everything is on demand. These cannot both stand. Phase 4 depends on the answer.

Done whenboth are written down once, in the COMMAND doc, and the losing version is deleted rather than left to resurface.
0.6Retire the superseded documentsHousekeeping

Move these out of the working set so nobody builds from them: Dispatch_ORDER_full (its "do all of it, don't come back" instruction is the opposite of your one-stage rule), DISPATCHv4buildspec (the final roadmap is a strict superset — nothing is lost), COWORKROADMAP v2 (describes a local backend, a Flutter client and no verified Claude call), and commanddesk_match.html (certifies an animated Nova you later dropped).

Done whenthe working set is the COMMAND doc, PROMPTS v3, the backend spec, and this roadmap. Nothing else.
0.7Collapse seven front ends to oneHousekeeping

Seven separate builds are in circulation and only full_system/frontend is live. The others have no login and post to the ungated chat path. Archive them somewhere clearly marked dead. Also clear the orphaned nova_blink.png and nova_mouth_1-4.png left in the live assets folder from the animated build.

Done whenone front end is the front end, and the rest are in an archive folder nobody deploys from.
Phase 1

Finish the original plan

1–2 days

Stages 0 through 4 are done. Stage 5 is the last one in the COMMAND doc, and it's the easy one by design — the pattern is already proven.

1.1Prove Stage 4 end to end on your phoneNeeds you

Draft and send are built, but the doc is explicit that nobody else can confirm this — you are the final eyes. Speak the ask, see the draft, say a listed yes, watch it send. Then check the audit log shows the exact word that opened the gate and the draft it was bound to.

One thing to expect: drafting needs the gmail.compose scope. If consent was only ever granted for readonly, this fails with a scope error. That's the named gate, not a bug.

Done whenyou have personally watched an email send, and the log names the word and the draft id.
1.2Stage 5 — clone the pattern to a second workerNot started

Same router, same permission-layer shape, same gate, same log. Swap the service and the instruction. The doc's own reasoning: this stage repeats a proven thing, so it carries almost no risk.

Calendar is the obvious candidate but it's the expensive one — see Phase 5. A cheaper second worker proves the clone works without opening that door.

Done whena second worker runs a request through the permission layer, logs it, and returns a result on the live site.
1.3Fix the test file's own run commandSmall bug

The docstring in test_compare.py says python -m oversight.test_compare, which raises an ImportError. The working command is python3 -m core.oversight.test_compare from backend/. A test suite nobody can start is a test suite nobody runs.

Phase 2

The enforcement core — on SQLite

3 days

This is the valuable half of the big roadmap, and none of it needs Postgres. Your permission layer already does exactly this for Gmail. This generalises it to everything else.

2.1policy.yaml and a loader that fails closedNot started

One file holding escalation tiers, priorities, loop rules and thresholds. The loader validates at startup and refuses to start on a malformed file rather than falling back to defaults.

The line that matters: an unknown action returns require_approval. An action nobody anticipated must never default to permitted.

Done whenget_escalation_tier("an_action_that_does_not_exist") returns require_approval, proven by a test.
2.2One execution path for every side effectNot started

Every agent action routes through enforcement.py, which checks policy before the action runs. Silent tiers execute and log. Notify tiers execute, log and emit. Approval tiers do not execute at all — they persist a pending record and hand control back to you.

Fail closed on error: if the policy lookup itself throws, the action does not run. The middleware becomes a single point of failure, so its failure mode has to be "nothing happens," never "everything is allowed."

Then audit for bypasses. Every file write, HTTP call, database mutation and outbound message that can happen without passing through this path is a hole. List any that can't be routed yet rather than quietly leaving them.

Done whena test agent told to delete a file cannot — even with its prompt edited to say approval isn't needed. Prompt says yes, enforcement says no, no happens.
2.3Version stamps on every writeNot started

Four strings — prompt, policy, schema, runtime — stamped by one write helper on insert. Existing rows backfill to 0.0.0, which honestly marks them as pre-versioning rather than pretending they were stamped.

This is what turns your audit log from a list into a record: without it you can't tell which prompt or which policy produced a given decision.

Done whena new row carries four real version strings without the caller passing them.
2.4Observer isolation, the SQLite wayNot started

The big roadmap wants a Postgres role with SELECT-only grants, and calls it the one guarantee that survives prompt injection. You can't have that on SQLite — there are no users and no GRANT.

What you can have: open Observer's connection as file:aire.db?mode=ro. That's a real refusal from the driver, not the application promising to behave. Weaker than Postgres — same file, no per-table control — but far stronger than a rule in a prompt.

Done whenan INSERT on Observer's connection raises from sqlite3 itself, proven by a test that attempts the write and asserts the failure.
Why this order

Phase 2 is worth doing before anything in Phases 3–5, because every feature added after it inherits the enforcement path automatically. Every feature added before it has to be retrofitted.

Phase 3

Something that can wake up on its own

3–4 days

Three features in your backend spec are impossible today for one reason: nothing in the system can fire on a timer. No APScheduler, no Celery, no crontab, no systemd timer. vault.py states it outright.

3.1Add the schedulerBlocks 3.2–3.4

A systemd timer or APScheduler inside the core process. Every job routes through enforcement.py from Phase 2, so scheduled work is under the same gate as anything else — a background job that can act unsupervised is exactly what shouldn't get its own private path.

Done whena trivial job fires on schedule and its run appears in the audit log.
3.2Per-app status updatesNot started

From the backend spec: a running account of what each worker has done in each app — "checked 3 emails, drafted 1 reply, nothing sent" — landing roughly once a minute. Not a live view, a steady heartbeat. Nova reads these and knows the state of play without operating anything.

Everything needed is already in the audit log and the actions table. This is a rollup query on a timer, not new instrumentation.

Done whenthe panel shows a running per-app account that updates without you asking.
3.3The nightly debriefNot started

Nova and the memory agent run a nightly pass: anything untouched lately, anything missed, anything old worth following up. The memory agent retrieves; Nova decides. Memory surfaces, the hub judges — that separation is the point.

Done whena debrief runs unattended overnight and its output is waiting in the morning.
3.4Replace lazy expiry with a real sweeperImprovement

Right now the 120-second confirmation window expires lazily — only when the next interaction happens. The safety property holds either way, because the gate stays shut unless the state and draft both match. But with a scheduler you can expire it properly, and the same sweeper catches tool_requested, reading, drafting and sending states that were left hanging.

Done whenan abandoned confirmation returns to idle on its own, and the timeout is logged.
Phase 4

Oversight, as originally specified

4–7 days

What got built is good but it isn't what the backend spec described. The spec wanted two independent accounts of the same work, cross-referenced. What exists compares stated intent against outcome — valuable, but a different check.

4.1The hub's own read-only view of each appNot started

From the spec: a link separate from the worker's, so you can open Nova and ask "what's been done in Gmail today?" and get a straight answer. The hub observes, the worker acts, and the wires don't cross.

Note this pulls against the current design, which deliberately funnels all Gmail through one path. The honest version is a read-only view over the audit log and actions table rather than a second Gmail connection — same answer, no second credential, no second thing to secure.

Done whenasking Nova what happened in an app today returns a real account drawn from the log.
4.2Two independent summariesNot started

The worker summarises its own work. A separate watcher agent summarises the same work. Both roll up. This is the check the spec actually asked for and it's genuinely different from intent-versus-outcome — it catches a worker that misreports, not just one that drifts from its stated plan.

Done whenone piece of work produces two summaries from two different agents.
4.3Nova adjudicates, and escalates when she can'tNot started

If the two summaries agree, fine. If they disagree, Nova flags it — that's the whole point of having two. Your own build note asks for the tiebreaker to be explicit: Nova adjudicates, and where she can't resolve it she escalates to you rather than silently picking one.

Today Angel writes to a review queue you read. There's no adjudication step and no path back through Nova.

Done whena deliberately mismatched pair of summaries produces a flag, and an unresolvable one reaches you.
4.4Red-flag alerting — blocked on your decisionYour call

The spec: anything clearly wrong should interrupt immediately, because a one-minute cadence can miss a fast mistake. The v3 prompts: nothing is ever pushed, everything is on demand.

A reasonable resolution is that both are right about different things — routine findings stay pull-only, and one narrow class (an action that already crossed the fence and shouldn't have) interrupts. But that's a call for you, not for whoever builds it.

Done whenthe rule is written down once, and the code matches it.
Phase 5

Calendar

1–2 weeks

The one item in the backend spec that was never started at all. It's also the hardest thing on this list, and it's worth being blunt about why.

Email works as text — the message that arrived, the reply that was drafted, side by side. Calendar doesn't. You need to see it, and Google Calendar won't embed. So it has to be Command Desk's own view backed by a genuine two-way sync.

Two-way sync is where projects like this die. Not the reading, not the writing — the reconciliation. An event changed in both places between syncs. A deletion that might be a deletion or might be a failed fetch. Recurring events, where a single edit can mean this instance, all instances, or this and everything after. Time zones across daylight saving. None of that is exotic; all of it has to be decided rather than discovered.

5.1Read-only calendar view firstNot started

Pull events, render a real view, let agents read it to brief and plan. No writes at all. This is the same shape as Stage 3's read-only Gmail proof, and for the same reason: prove the connection where nothing can be damaged.

Done whenyour real week renders in Command Desk and Nova can describe your day.
5.2Writes, behind the gateNot started

Creating or moving an event is an action with consequences — it can land in someone else's calendar. Through the permission layer, behind confirmation, exactly like send. Same exactly-once guard: a lost network reply must never become two meetings.

Done whenyou speak an event, see it, confirm it, and it appears in Google Calendar once.
5.3Two-way sync and conflict resolutionDesign first

Decide the rules before writing code: which side wins a simultaneous edit, how a deletion is distinguished from a failed fetch, what happens to recurring-event edits, and how far back a sync reaches. Write them down, then build to them.

Done whena change made in either place appears in the other, and a deliberate simultaneous edit resolves the way the written rule says it should.
Phase 6

The Postgres question

3–6 weeks — conditional

The final roadmap assumes PostgreSQL throughout: roles and grants, jsonb, timestamptz, row-level security, Terraform, RDS. You're on SQLite. This phase is where that gets resolved — or deliberately doesn't.

Ask this before committing

Row-level security, tenant_id and Postgres roles exist to keep different customers apart. If Command Desk is one person on one box, that's a month spent on a problem you don't have yet — and one you can solve later, when a second user is real rather than hypothetical.

Phase 2 already gives you the fail-closed policy engine, the single enforcement path and a real read-only handle for Observer. That's most of the protection, for about three days.

If you do go ahead, the order is fixed and the migration itself is the risk — moving a live database with real sessions, real memory and a real inbox history is a project in its own right, not a step.

  1. Reversible migrations first. Every migration gets a matching down script, applied as an atomic batch, tested up-then-down against a clean database in CI before anything touches AWS. One untested down script is the difference between a bad afternoon and a disaster.
  2. Event bus. Eleven event types, persisted with version stamps, indexed on the unhandled-queue lookup because it runs constantly. Hub subscribes rather than polls.
  3. Hub's completion guarantee. A background processor works unhandled events oldest-first to a resolution — completed, escalated, or explicitly superseded. Never blocks foreground work. A pending approval past its 72-hour expiry escalates; it is never auto-approved and never quietly dropped.
  4. Observer as a real database role. SELECT only, on named tables, public grants explicitly revoked, credentials in Secrets Manager, created by a migration so it's reproducible. This is the step Phase 2 could only approximate.
  5. Thresholds as SQL. Five parameterised queries with values injected from policy. The query decides whether a threshold was met; Observer only explains what the rows mean.
  6. Decisions table. Evidence references required — a decision with no evidence isn't recorded as a decision. Three confidence values stored separately, never averaged into one number.
  7. Health as counts. If a number can't come from a live query it isn't displayed. No percentage without both numerator and denominator visible. An empty result shows "no data" — never 0%, never 100%.
  8. Semantic judgments as fields. The model writes drift_detected, same_issue_as_prior, role_drift. Policy decides the consequence. The prompt holds the judgment and never the consequence.
  9. Prompt editor versioning. Bump on every save, all prior versions immutable and retrievable, reject a save that would overwrite without a bump.
  10. Slim the prompts — last. For every remaining sentence, ask whether it's enforced somewhere. If it is, delete it from the prompt. A rule stated twice drifts out of sync.

Open

Decisions nobody else can make

  • Memory window — fourteen days as the backend spec says, or four as the code says.
  • Alerting — interrupt on a red flag, or on demand only. Phase 4.4 waits on this.
  • Postgres — migrate, or stay on SQLite and accept the weaker Observer boundary.
  • Second worker — which service Stage 5 clones to.
  • Retention — how long conversations, planners and threads are kept. The spec says design it as a setting, not a hardcode, and tune by trial.
  • Vault placement — separate agent or folded into the hub. Your stated lean is separate, to keep load off Nova.
  • Calendar conflict rules — which side wins, and what a deletion means. Decide before 5.3, not during.

Out

Ruled out — do not build

  • Claude or ChatGPT running inside Command Desk as embedded apps, and any attempt to wire Claude-with-its-full-tools into the system. You wanted a closed loop with Claude keeping its native tools; it isn't available, and you've decided. They can still appear as pickable apps — the "operates them live in the frame" path is not a target.
  • Anything relying on embedding an app that blocks it. Assume Gmail, Calendar and Maps cannot be shown in an iframe. The backend link plus per-app updates is the substitute.
  • Video Nova. Dropped entirely. The original still image, no loop, no motion.
  • Browser-based speech-to-text. The engine doesn't exist in iPhone Safari, so it can never work as built. The mic stays parked until the phone-records-then-Whisper-on-the-box path is built as a phone app.
  • Rebuilding the permission layer, state machine, auth or oversight. They work, they're tested, and replacing them would cost weeks to land somewhere worse.
